Self-review examples for data engineers.

Data engineering shows up in other people's work. The analyst's chart is right, a product question gets answered in an hour, the model trains on yesterday's data. Your self-review has to trace those back to the pipelines and tests you built.

What reviewers look for in a data engineer

  • Freshness and reliability. Pipelines that land on time, and how often they didn't.
  • Data quality. Tests, contracts, and bad data caught before a dashboard showed it.
  • Speed and spend. Run times and warehouse spend for the jobs you own.
  • Self-serve. Datasets and docs that let people answer questions without a ticket to you.
  • Safe schema change. Evolving tables without breaking the people downstream.

Example: impact

The projects, people and numbers in these examples are made up. Keep the shape and use your own facts.

Impact • Rebuilt the daily recipe-events pipeline as incremental models. Run time fell from about 3 hours to 25 minutes, and the job's warehouse spend roughly halved. • Added tests (unique, not null, freshness) to the 12 most-used tables. They caught four upstream schema changes before any dashboard broke. • Published the Sync SDK usage dataset with column docs. Product answers adoption questions themselves now; requests to us about sync data have almost stopped.

Your users are other people in the company. Write the effect in their terms: answered without a ticket, right the first time, ready by 9.

Example: collaboration

Collaboration • Agreed an event schema contract with the mobile teams, written with Neha. New events arrive named, typed and documented, instead of being fixed after launch. • Ran weekly office hours for analysts. Most questions became docs, so the same question rarely came twice. • Worked with Ravi to move pipeline alerts into the team's on-call, with a runbook for each failure we'd seen.

Example: growth

Growth • Learned streaming ingestion on a small project: sync events now land within five minutes, for the one dashboard that needs it. • Wrote my first design doc for a cross-team change (the event contract) and ran the review myself. • Next half: lineage for the top 20 tables, so anyone can see what breaks before they change a column.

Phrases that land

  • "landed on time on 178 of 182 days": freshness as a record, with the misses included.
  • "caught before any dashboard broke": the failure you prevented, in the reader's terms.
  • "from 3 hours to 25 minutes": speed someone downstream felt.
  • "answer it themselves, without a ticket": self-serve, measured.

Phrases that don't

  • "Built pipelines." That's the job title. What do they make possible?
  • "Maintained the ETL." Against what? Say what broke, and what didn't.
  • "Worked with stakeholders." Name who, and what they could do afterwards.
  • "Big data." Say what the size made possible, or what it cost.

Gather your evidence

New models are the clearest trail in a data repo. This lists the SQL files you created in the last six months:

git log --since="6 months ago" --author="$(git config user.email)" --no-merges \ --diff-filter=A --name-only --format='' -- 'models/*.sql' | sort -u

Then pull the orchestrator's run history for your pipelines (success rate and duration over time), the warehouse query history for the jobs you tuned, and the test failures that caught bad data before anyone saw it.
